# Taste
- Prefers starting with a small proof-of-concept before committing to a full implementation; asks to "start with" a minimal, self-contained artifact first. Confidence: 0.75
- Prefers browser-only / serverless solutions: code should run entirely client-side with no server logic. Confidence: 0.7
- Prefers reusing existing packages/CDN bundles where they fit before building a custom equivalent, but will approve building a custom host when the existing one cannot meet the goal. Confidence: 0.5
- On Windows, prefers the user-local .NET SDK (`%USERPROFILE%\.dotnet\dotnet.exe`) over the one on `PATH`, because the PATH install lacks the needed `wasm-tools` workload. Confidence: 0.65
- Prefers consolidating shared dependencies into a single bundle/package rather than shipping duplicates; asks whether a new artifact can also replace an existing implementation to reuse its dependencies (Roslyn, runtime, reference assemblies). Confidence: 0.6
- Expects the agent to keep iterating autonomously until the feature actually works and the artifact is packaged/ready for use, rather than stopping at a blocker or a documented "deferred" finding; "keep iterating till X works". Confidence: 0.65
- Prefers finishing a feature in its own standalone project before wiring it into the consumer/main repo (e.g. "Do not change LiveCodes for now — let's complete the Blazor support first"); integration is a separate, later step. Confidence: 0.75
- Prefers explicit, conventional field names in data shapes, e.g. `{filename, content}` for project files rather than `{name, content}`. Confidence: 0.55
- Prefers demo/starter projects that exercise the real capability — several files with cross-file references, mixing languages (`.razor` + `.cs`) — rather than minimal single-file snippets, and checks that the shipped demo actually loads/uses every new feature (repeatedly flagged that the demo wasn't loading the new worker rather than accepting it as intentionally disabled in the demo, and verifies the demo's real browser behaviour himself). Confidence: 0.65
- Wants tooling/simulations to faithfully match the real local development environment and standard toolchain behavior (e.g. behave exactly as `dotnet build` would) — values fidelity over convenience, and questions shortcuts that make the tool more permissive than local dev ("I want to match local development environment as much as possible"). Confidence: 0.75
- Distinguishes committed artifacts from build output: wants deployable artifacts (`package/`, `refs/`) tracked in git so a checkout is usable without the toolchain, but build output (`bin/`, `obj/`) never committed; edits `.gitignore`/drives the ignore rules to match. Confidence: 0.7
- Prefers hardcoded assumptions/constants be exposed as configurable options rather than fixed values (e.g. asked to make the root namespace a configurable parameter instead of a built-in default). Confidence: 0.5
- Cares about backward compatibility: when a feature grows (e.g. multi-file project support), expects previously-working simpler modes (single-file / no `_Imports.razor`) to keep working, and proactively asks whether they still do. Confidence: 0.55
- Cares about startup/download payload size and prefers fetching only what is needed on demand (e.g. lazy-loading assemblies) instead of downloading the whole framework/toolchain up front. Confidence: 0.5
- Willing to rewrite git history to remove unwanted content (e.g. `git filter-branch` to purge `bin/`/`obj/` from past commits), not just stop tracking it going forward. Confidence: 0.6
- Wants claims backed by real measurements, not estimates: asks "how does X compare to Y" and expects figures taken from a real browser/runtime and shown side by side (tables), ideally with the measurement method stated. Confidence: 0.65
- Prefers a README that leads with a plain one-paragraph description plus a working quick-start snippet (including required options such as `baseUrl`) before any internals; wants a proper repo/library README, with detailed session findings, measurements and traps moved out into a separate `FINDINGS.md` at the repo root. Confidence: 0.7
- Prefers docs to mention a predecessor/competing implementation only where it is concretely relevant (e.g. as a size comparison line), not to explain that other project's internals or history. Confidence: 0.55
- Asks before committing and approves every time, often with a bare "commit" or "yes, commit it" and no further instruction; expects the agent to prompt for approval rather than commit unprompted, and one focused commit per completed, verified change with the rationale in the message body. Confidence: 0.65
- For larger or risky changes, prefers a short ranked menu of options with an explicit recommendation, then picks one ("Yes, go with option 1"). Confidence: 0.55
- When a design decision touches framework convention, asks what the framework itself does versus what developers normally do, i.e. prefers idiomatic solutions that match standard practice over custom invention. Confidence: 0.55
- Expects a package to be genuinely publish-ready before it goes out: LICENSE file present, README inside the package root, complete manifest metadata (author, keywords, homepage, bugs), and the exact artifact that will be published validated/smoke-tested first. Confidence: 0.6
- Cares about main-thread responsiveness and looks to move resource-intensive work (e.g. compilation, payload fetching) off the main thread into a web worker; notices and reports UI freezes during load/startup itself ("most of the loading time, the page is not responsive"), not just whether a feature eventually completes. Confidence: 0.7
- Prefers web workers constructed from a `data:` URL (whose body is just `importScripts('<baseUrl>worker.js')`) rather than a Blob URL, so the worker script stays versioned with the bundle and can still reach a cross-origin script. Confidence: 0.7
- Explicitly rejects `SharedArrayBuffer` ("DO NOT USE") and prefers approaches that avoid cross-origin-isolation / special response-header requirements (COOP/COEP/CORP) so the bundled code works on arbitrary pages. Confidence: 0.7
- Wants an explicit, honest inventory of what is verified-working versus untested or known-missing per feature area (e.g. Blazor rendering, routing, CSS/assets, C#, console), and tracks caveats the agent flagged earlier — expects a previously-noted gap to be closed or carried forward, not quietly dropped ("I remember you mentioned that there is something missing or you did not confirm it works"). Confidence: 0.6
- Scopes requirements from the downstream consumer's needs: when a capability is announced as "used in LiveCodes", expects the public API shape (argument order, e.g. `RunCode(source, stdin)`) and behavior to line up with exactly how the integration will call it, and treats making that path work as the priority over adding new capability. Confidence: 0.5
- Expects a capability to be verified end-to-end from the consumer's side — a real program actually exercising it (reading stdin) — not just that the supporting call/plumbing was invoked; an unverified path is treated as missing work. Confidence: 0.55
- Weighs added complexity against demonstrated benefit: if a new mechanism (e.g. a web worker) does not measurably resolve the reported problem, prefers reverting it and returning to the simpler solution ("revert this and go back to no worker solution, since most of the hanging time is not solved") rather than keeping speculative infrastructure. Confidence: 0.75
